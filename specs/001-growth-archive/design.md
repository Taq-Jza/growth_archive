# 设计方案 ·「成长档案」

> 版本 v2.8（2026-10-31）｜对应《需求规格书 v3.0》
> 本文件回答「怎么做」，每个设计决策标注它服务于哪些功能编号 `F-xx`

---

## 1. 设计目标

| 目标 | 来源 | 说明 |
|---|---|---|
| 短期内可交付、可演示 | 项目约束 | 一切选型以「今天能跑通」为准 |
| 每条需求可追溯、可验收 | 工程要求 | 需求 → 设计 → 任务 → 代码 → 证据，链路不断 |
| 模型不可用时不崩 | N-03 | AI 是增强，不是依赖 |
| 单机可部署、零外部依赖 | 部署要求 | 新用户打开链接即可使用 |

## 2. 总体架构

```
┌─────────────────────────────────────────────┐
│  浏览器（服务端渲染 HTML + 少量原生 JS）        │
└──────────────────┬──────────────────────────┘
                   │ HTTP
┌──────────────────▼──────────────────────────┐
│  FastAPI 应用                                │
│  ├─ 路由层    main.py（页面与表单）            │
│  ├─ 服务层    ingest / search / rag / cards   │
│  ├─ 领域层    textproc（分词·切块·高亮）        │
│  └─ 接入层    llm（模型调用，可降级）           │
├─────────────────────────────────────────────┤
│  SQLite（业务数据 + FTS5 全文索引）             │
└──────────────────┬──────────────────────────┘
                   │ HTTPS（可选，失败即降级）
┌──────────────────▼──────────────────────────┐
│  模型服务（CodeArts 提供的 GLM / DeepSeek / Kimi）│
└─────────────────────────────────────────────┘
```

**分层原则**：路由层不写业务逻辑；服务层不碰 HTTP；`llm` 层是唯一知道外部服务存在的地方，便于替换与降级。

## 3. 关键技术决策

### D-01 用 SQLite 而非 PostgreSQL（服务 F-01 ~ F-08）

- **决策**：单文件 SQLite，业务表 + FTS5 全文索引同库。
- **理由**：单用户、25 篇文档、约 200 切片。SQLite 零运维，部署时不用装数据库服务，省掉约 5 小时环境调试；FTS5 原生支持 BM25 排序。
- **代价**：并发写入弱。单用户场景下可接受。
- **可逆性**：SQL 只用标准语法，迁移到 PG 只需替换 FTS 实现，服务层不动。已记入宪法豁免附录。

### D-02 混合检索：关键词 + 语义，RRF 融合（服务 F-04、F-05）

- **决策**：两路并行召回各 Top20 → RRF 融合 → 模型重排取 Top5。
  语义路用 bge-m3（1024 维），向量以 JSON 存在切片表，检索时全量读入内存做余弦比对。
- **为什么两路都要**：
  关键词在专有名词上准（「蓝桥杯」直接命中），语义在换说法时强。
  实测「有没有做过跟自然语言处理相关的东西」：关键词路召回的是《英语文献阅读》《程序设计竞赛》，全部跑偏；
  语义路第一条就是《文本情感分类实验》。融合后它排第一。
- **为什么不用向量数据库**：300 个切片，全量余弦是毫秒级。
  为一个索引引入 pgvector 或独立向量库，收益不抵部署复杂度；真要上十万级，替换 `semantic_search` 内部实现即可，`retrieve()` 入口不变。
- **代价**：每次问答多一次 embedding 调用（约 100–200ms）；换 embedding 模型需全量重算（`scripts/embed_backfill.py --rebuild`）。

### D-03 服务端渲染，不引前端框架（服务所有页面）

- **决策**：Jinja2 模板 + 原生 CSS（Tailwind CDN），无构建步骤。
- **理由**：5 天内没有时间处理前端构建、状态管理、路由；服务端渲染改一行就能看到效果。
- **代价**：交互不如 SPA 顺滑，流式输出需要一段原生 JS 处理 SSE。

### D-04 模型接入抽象 + 三级降级（服务 F-04、F-05、F-06）

- **决策**：`llm.py` 只暴露 `chat()` 与 `chat_stream()`，底层走 OpenAI 兼容协议，`base_url` / `api_key` / `model` 全部来自环境变量。
- **三级降级**：

| 级别 | 触发条件 | 行为 |
|---|---|---|
| L0 正常 | 模型可用 | 正常重排、生成、蒸馏 |
| L1 重排失败 | 超时 / 返回非法 | 用关键词召回顺序，问答继续 |
| L2 生成不可用 | 接口报错 / 无 key | 返回「模型服务暂不可用」+ 直接展示检索到的原文 Top3，功能不白屏 |

- **理由**：N-03 要求模型故障不影响核心功能。降级本身就是演示素材。

### D-05 中文检索用 jieba 侧分词 + FTS5（服务 F-03）

- **决策**：Python 侧用 jieba 把中文切成空格分隔的串，写入 FTS5（`unicode61` 分词器）。
- **理由**：避开了中文分词器（zhparser）的编译与部署；索引侧与查询侧用同一分词器，保证一致性。
- **代价**：新词识别依赖 jieba 词典，专业术语可能需要自定义词典（课程名、公式名）。

### D-06 切片策略：段落优先，句末次之（服务 F-02）

- **决策**：先按空行分段；段超过 450 字则按句末标点切；块间重叠 80 字。
- **理由**：切片质量决定检索质量。句中截断会产生"半句话"片段，模型读到会误解。
- **代价**：切片长度不完全均匀，但语义完整优先于长度整齐。

### D-07 引用可核对：存原文偏移而非仅存 ID（服务 F-05）

- **决策**：引用记录 `chunk_id` 与片段原文，前端点击跳转到文档详情并按片段定位高亮。
- **理由**：AC-05-4 要求引用与原文逐字一致。存原文副本才能做到"可校验"，而不只是"有个出处"。
- **代价**：存储冗余，可接受。

### D-08 卡片蒸馏强约束 JSON（服务 F-06）

- **决策**：prompt 中给出精确 JSON Schema 与示例；解析失败重试 1 次；以 `document_id` 为键覆盖写入。
- **理由**：模型输出不稳定是常态；幂等键保证重复蒸馏不产生重复卡片（AC-06-4）。

### D-09 复习间隔用固定表而非 SM-2（服务 F-07）

- **决策**：阶段 0–4 对应 1/3/7/15/30 天。
- **理由**：SM-2 需要难度因子与多次调参，5 天内调不准；固定表可解释、可验证、可演示。

### D-10 示例库作为一等公民（服务 F-08）

- **决策**：26 条成长记录（课程 8 / 技能 7 / 竞赛 5 / 项目 4 / 特长 2）+ 15 张预置要点卡 + 3 段预置 JD，随仓库提供，一键载入。
- **理由**：新用户不会先积累一学期的经历再来试用。没有示例数据，所有 AI 功能在首次打开时都是空的。

### D-11 岗位匹配 = 检索 + 证据组织，不是"让模型写简历"（服务 F-07）

- **决策**：把 JD 拆成要求条目 → 逐条去档案里检索证据 → 按固定规则算分 → 只在"措辞"环节用模型。
- **理由**：
  1. 让模型直接写简历，必然编造数字与奖项，这在求职场景是**致命错误**；
  2. 拆解后再检索，每一条结论都能落到具体记录 ID，可追溯、可验收；
  3. 匹配度由分维度加权（技能 0.4 / 经历 0.4 / 成果 0.2）**计算得出**，不是模型打分 —— 模型打分不可复现，也无法验收 `AC-07-5`。
- **代价**：比"一句话生成简历"多两次模型调用，但换来可验证性。
- **简历条目约束**：模型只负责把「命中的记录片段」改写成 1–2 句通顺表述，改写前后的实体（数字、奖项、时间）必须一致，否则丢弃该条。
- **全局相关性闸门**（实现中补上的关键设计）：
  逐条判断「这条要求有没有命中」是不够的 —— 模型给的关键词里常混有「一门」「说明」这类噪声，
  逐条门槛要么漏判、要么误判。因此改为看**整体覆盖率**：
  命中要求数 / 总要求数 < 34%，或证据只来自单一记录且覆盖率 < 60%，判为「档案与该岗位无关」，
  总分置 0、不生成任何简历条目、提示用户补充经历。
  实测：数据分析岗 86%、后端岗 100%、厨师岗 33%（触发闸门）。

### D-12 检索的三级降级（服务 F-04）

- **决策**：
  - L0：关键词 + 语义双路 RRF 融合（正常态）
  - L1：语义路不可用（无密钥 / 接口异常 / 该用户还没有向量）→ 纯关键词，`mode=keyword`
  - L2：关键词也无命中 → 明确拒答，而不是硬凑
- **入库侧的容错**：向量生成失败不影响记录写入 —— 文本已入库、关键词能搜到，只是暂不参与语义检索，
  之后跑 `scripts/embed_backfill.py` 补上。**写数据永远比生成向量重要。**

### D-13 分类导航用独立页面，不做下拉筛选（服务 F-12）

- **决策**：五类记录各有独立页面 `/c/{kind}`，左侧固定导航切换；移动端折叠为横向滑动条。
- **理由**：下拉筛选把不同类型的记录压成同一种列表，用户看不出「竞赛是时间线、项目是卡片」这种差异；
  独立页面才能按类型设计最合适的呈现方式。
- **代价**：多五个路由和一套模板分支；导航项变多，移动端需要横向滚动。

### D-14 图表服务端生成 SVG，不引图表库（服务 F-12）

- **决策**：饼图与条形图由 `charts.py` 生成 SVG 字符串，直接嵌入页面。
- **理由**：只有一个饼图，引 Chart.js（约 200KB）不值当；而且外部资源曾因 CDN 不可达导致整站无样式，
  这类依赖能少一个是一个。服务端生成还能保证首屏就渲染出来，不闪。
- **代价**：图表能力有限（无交互、无动画）。真要做复杂图表再换库。

### D-15 多格式导入按类型分流，图片走多模态（服务 F-11）

- **决策**：文本类本地解析（txt/md 解码、docx 用 python-docx、pdf 用 pypdf），
  图片压缩到最长边 1600 后用视觉模型转写。
- **理由**：本地能解的绝不动模型，省钱又快（md/docx 是毫秒级）；图片没有别的办法，只能上多模态。
  压缩是必须的 —— 手机原图 3MB，base64 后 4MB，很容易超请求体限制。
- **代价**：图片识别依赖模型可用性与额度，且有一次网络往返（实测约 1.7 秒/张）。
- **失败处理**：扫描版 PDF（无文字层）明确提示改用图片，绝不产出空记录。

### D-16 课程助手强制「每句挂引用」（服务 F-10）

- **决策**：模型输出的每一句解释必须带资料片段编号，编号不存在或缺失的句子**直接丢弃**，
  并在界面上告知丢弃了几句话。
- **为什么这么严格**：实测中模型会用课外知识回答资料没覆盖的问题
  （问「L1 为什么稀疏」，示例资料里根本没有 L1/L2，模型却讲得头头是道）。
  课程场景下，「讲得漂亮但资料里没有」比「答不上来」危险得多 —— 学生没法分辨。
- **代价**：回答可能变得保守、甚至拒答。这是有意为之的取舍。

### D-17 编辑记录必须重建派生数据（服务 F-13）

- **决策**：改正文时删掉旧切片与索引 → 重写正文 → 重新切块建索引 → 重新生成向量 → 清空旧要点卡。
- **理由**：切片、索引、向量、卡片全是派生数据。只 UPDATE 主表会出现「正文改了、搜不到新词、
  卡片还在讲旧内容」这种最难排查的问题。
- **代价**：编辑比新建慢（要重新调 embedding），且用户需要重新提炼卡片 —— 界面上要明说。

### D-18 发生时间精确到日，旧数据启动时补齐（服务 F-02、F-03）

- **决策**：`period` 存 `YYYY-MM-DD`；录入与筛选都用 `<input type="date">`。
  早期只记到月的旧记录在 `init_db` 时补成当月 1 日，条件为 `length(period)=7`，可重复执行。
- **理由**：记录一多，按月筛选等于没筛 —— 一个月里可能挤着十几条，用户还是得肉眼找。
  成本几乎为零：SQLite 的 TEXT 存日期，字符串比较即时间比较。
- **为什么不存时间戳**：这里存的是「这件事发生在什么时候」，不是「这条数据什么时候写进来的」。
  两者必须分开，`created_at` 已经有了。
- **迁移策略**：写库统一在 `ingest._norm_period` 收口，避免 seed / 人工录入 / 编辑三条路径各行其是。

### D-19 放大视图用同心圆，不用「饼图套饼图」（服务 F-12）

- **决策**：点进某个能力域后，用**多层同心圆环**表示该域下各细分条目的占比，一层对应一个条目。
- **理由**：
  1. 嵌套饼图（sunburst）要么需要额外库，要么手写路径极易出错；
  2. 同心圆每层都用同一个圆心和 `pathLength=100` 归一化，几何上只是半径递减，实现稳定；
  3. 层与层的长度可以直接横向比较，比嵌套扇区的角度比较更直观。
- **代价**：条目多于一屏可读层数时，视觉会挤。策略是环宽随层间距自适应（最细 5px），
  信息完整性由右侧标签列表兜底 —— 图形负责「感觉」，列表负责「数字」。
- **颜色**：同一能力域内用父色的明度梯度（逐层混白），而不是跨域撞色，
  这样一眼能看出「这些层属于同一个能力域」。

### D-20 放大视图：左图右标签，容器内滚动（服务 F-12）

- **决策**：放大层绝对定位占满能力分布卡片；内部两栏（左图 / 右列表），
  内容用 `min-h-full` 自适应，溢出走容器内 `overflow-y-auto`；返回键固定左上角。
- **理由**：早期版本把圆环放中间、标签全部居中堆在下面，条目一多就顶出卡片底边，
  被 `overflow-hidden` 裁掉 —— 看起来就是「溢出了」。根因是「纵向堆叠 + 固定高度」这个结构，
  不是某个 margin 写错了。改成横向分栏后，纵向压力转移到列表自身的滚动，结构上就不可能溢出。
- **代价**：小屏仍是单列，需要额外给卡片更高的 `min-height`；这点用媒体查询单独处理。

### D-21 视觉系统：一个主色 + 两档缓动（服务全局）

- **决策**：配色收敛到单一主色 `#0D9488`，辅色只用于数据可视化（饼图/同心圆）。
  动效只用两档缓动：入场 `cubic-bezier(.16,1,.3,1)`（expo-out，自然收尾），
  交互 `cubic-bezier(.4,0,.2,1)`（standard）；时长 150ms（按压）/ 220ms（悬停）/ 550–650ms（入场）。
- **理由**：早期版本的问题是「什么都有颜色、什么都在动」——
  青绿 + 靛蓝 + 琥珀 + 玫瑰 + 青柠五个强调色同时出现，加上 scale + translateY 同时作用的悬停，
  视觉上必然嘈杂。收敛之后，「重点」才有位置。
- **代价**：图表之外没有任何彩色，克制到近乎朴素；这类界面靠留白和层级取胜，不靠颜色。
- **落地方式**：全部走 CSS 变量（`--ink-1..4` / `--brand*` / `--sh-*` / `--ease-*`），
  模板里不再出现硬编码色值 —— 换主题只需改一处。

### D-22 页面跳转用原生 View Transitions，不引前端框架（服务 N-07）

- **决策**：用 `@view-transition { navigation: auto }` + `::view-transition-old/new` 自定义过渡；
  同时加一条顶部路由进度条，在点击链接/提交表单的瞬间给出反馈。
- **理由**：这是 MPA（服务端渲染）架构，页面跳转本来就是浏览器行为。
  为了「转场动画」引入前端路由框架，等于为了一个视觉效果重构整个架构，得不偿失。
  View Transitions 是浏览器原生能力，写十几行 CSS 就够；不支持的浏览器自动降级为普通跳转。
- **代价**：Safari / Firefox 目前支持不完全，跨浏览器体验不一致；但降级路径是无害的。

### D-23 排序口径收敛到 `browse()` 一处（服务 F-06、F-12）

- **决策**：`time / time_asc / kind / tag` 四种排序全部在 `search.browse()` 里实现，
  分类页、要点卡页、概览列表共用，只在各自的 ORDER BY 上分叉。
- **理由**：排序规则一旦分散到三个路由里，就会出现「概览按时间、分类页按 id、
  要点卡按创建时间」这种最难解释的不一致。收敛一处后，加一种排序只改一个地方。
- **坑**：按标签排序时，「主标签」必须排除类型名。否则第一条标签常常是「课程」，
  按标签排序就退化成了按分类排序 —— 这个 bug 是在实测里才发现的。

### D-24 环形图用「圆头描边 + 笔宽封顶」，而不是扇形路径（服务 F-12）

- **决策**：每段用 `<circle>` 配合 `stroke-dasharray` 画，`stroke-linecap="round"`；
  笔宽取 `min(厚度, 弧长 × 0.92)`，路径长度 = 弧长 − 笔宽 − 缝隙。
- **理由**：扇形路径的两端是直角，六段拼在一起像齿轮；圆头端点天然带圆弧，
  缝隙处形成柔和缺口，观感更「灵气」。但圆头会向两端各多出半个笔宽——
  1 条记录只占 4%，弧长 18px 而笔宽 30px，会鼓成一颗压住邻段的圆珠。
  按弧长给笔宽封顶后，小段自动收成 16px 的小圆点，既不压邻段也不显得错位。
- **代价**：小段的厚度与主段不一致（这是有意的：小占比就该轻一些）；
  缝隙需要显式扣除，否则圆头会让段与段贴在一起。
- **配色**：换成同明度的高饱和六色（`#0FB5A8 / #F5A623 / #4C7DF5 / #F0567F / #84C93C / #8B5CF6`），
  并把五类记录的颜色也从同一组取（`KIND_COLORS`），避免「图表一套色、标签另一套色」。

### D-25 入场动效的隐藏条件必须可回收（服务 N-11、N-12）

- **决策**：`.reveal` 仅在 `html.js` 存在时才设 `opacity:0`；方向由 `data-anim` 决定
  （up / down / left / right / zoom）。**动态插入的列表项改用 CSS animation（`.rec-in`），
  不用 transition + IntersectionObserver。**
- **背景**：上一版「按分类」列表只剩分组标题、下面全空 —— 局部刷新注入的 `.reveal`
  没有被页面加载时的观察器接管，元素永远停在 `opacity:0`。
  这是最坏的一类 bug：动画「正常」，内容却不可见。
- **理由**：animation 在节点插入时自动播放，不依赖任何 JS 状态；
  transition 需要外部加 class，一旦观察器没接上就静默失效。
  同时保留 `window.scanReveal(root)`，供其他需要滚动揭示的局部刷新调用。
- **方向分配**：同一区块内方向一致，区块之间有区分 ——
  概览标题从左、快速捕获从上、三张统计卡左/上/右汇入、能力分布从右、要点卡两列左右交替、
  记录列表向上；分类页项目卡左右交替，时间线向上。

### D-26 概览的「+」直接复用现有上传接口（服务 F-02b）

- **决策**：加号触发隐藏的 `<input type=file>`，选定后把当前类型下拉的值写进隐藏表单，
  `requestSubmit()` 提交到既有的 `POST /upload`。
- **理由**：上传、解析、入库、跳转这条链路在 F-11 已经打通；
  再写一个「从概览直接建记录」的接口等于复制一份逻辑，两处迟早不一致。
  前端只负责把「文件 + 类型」塞进已有表单。
- **细节**：用 `requestSubmit()` 而不是 `submit()` —— 后者不触发 `submit` 事件，
  顶栏的路由进度条不会亮；识别图片要几秒，没有反馈用户会以为没点上。

### D-27 环形图：环宽恒定 + 极小切片并入「其他」（服务 F-12）

- **决策**：所有段用同一厚度（28px）；占比 <5% 的能力域合并成「其他」一段，
  合并后段数控制在 5–6 段，图例注明「含 N 类」，点开可见明细。
- **理由**：上一版为了让 4% 的小段也能看见，按弧长给每段单独算笔宽，
  结果就是「同一个环，粗的粗、细的细」—— 读者会误以为粗细代表大小。
  主流做法（Figma/ECharts/各类 dashboard 的环形图）都是**环宽恒定**，
  段数超过 6–7 个或占比过小就并成 Other。
- **代价**：小占比的类别不再单独成段，需要点开「其他」才能看到明细。
- **细节**：圆头端点会向两端各多出半个笔宽，所以路径长度 = 弧长 − 笔宽 − 缝隙，
  起点前移半个笔宽，视觉边界才与真实占比对齐。

### D-28 「按分类」是文件夹，不是分组长列表（服务 F-12）

- **决策**：概览切换「按分类」时，先给五张分类文件夹卡（名称、条数、最近三条标题），
  点进去进入该分类页；不再把记录按类摊开。
- **理由**：分组标题只是给长列表加了几行标签，记录一多依旧要一直滚。
  文件夹是「先选范围、再看内容」的两级结构，条目越多收益越明显。
- **代价**：多一次点击；总量少的时候反而绕。
- **取舍**：只在「按分类」这一视图这么做，「最新」仍是完整列表 —— 两种浏览习惯都保留。

### D-29 全屏阅读用 html 状态类，不新建弹层（服务 F-13）

- **决策**：点「全屏阅读」时给 `<html>` 加 `reading-full`，把正文那一块临时变成
  `position:fixed; inset:0`，同时隐藏顶栏、侧栏与页脚；退出即移除类。
- **理由**：不搬家 DOM，滚动位置、引用高亮、已加载的卡片状态都不会丢；
  若另做一个弹层复制正文，两份内容迟早不一致（尤其是引用高亮这类依赖 DOM 的功能）。
- **坑**：顶栏带 `backdrop-filter` 与 `sticky`，实测会盖在固定层之上，
  所以必须显式 `display:none`，不能只靠 z-index。
- **细节**：正文是纯文本（`white-space:pre-wrap`），没有子元素可以限宽，
  用左右 `padding: max(24px, calc((100vw - 760px)/2))` 把文字夹到 760px。

### D-30 图片两种模式：默认「按文字重排」，模型重绘留作可选（服务 F-11）

- **决策**：上传图片时可以选「保留原图」或「重排成整洁笔记」。重排默认由本地渲染完成：
  用视觉模型识别出的文字重新排版成一张笔记图；`IMAGE_REDRAW=ai` 时才调用图生图模型。
- **为什么不是一上来就用模型重绘**：实测 `Qwen/Qwen-Image-Edit-2509`，同一张中文笔记
  两次结果分别是「漏掉两行、把提示词『整洁的电子笔记』画进正文」与「第三行文字重叠成乱码」。
  中文长文本的图像编辑目前不可靠，而这类错误对学习资料是致命的 —— 看起来像笔记，内容却是错的。
- **代价**：重排后的图是纯文字排版，原本的手绘箭头、示意图会丢失 —— 所以原图必须保留，
  记录页提供「原图 / 重排」切换。
- **收益**：重排几十毫秒完成、零成本、逐字可控；比模型重绘快两个数量级。

### D-31 知识图谱：模型只做「分章」，布局由代码算（服务 F-14）

- **决策**：模型负责给每条记录判断章节、抽关键概念，结果落 `doc_kg`；
  图的坐标由 `kg.layout()` 用固定规则计算：中心 → 章节（内圈）→ 记录（外圈）。
- **理由**：让模型直接产出坐标既不稳定也不可复现，同一份数据每次图形状都不一样；
  拆成「抽取」与「布局」两段后，抽取结果可缓存、图可以稳定重绘。
- **分章口径**：章节名只写主题（「索引与查询优化」），不写「第 N 章」——
  不同课程的第三章会撞在一起，图上就无法分辨。
- **入口克制**：图不是默认视图，必须从分类页按钮进入；生成一次后直接读库，
  只有点「重新生成」才再次调用模型。

### D-32 粒子反馈只用一套色板（服务 N-14）

- **决策**：点击导航、按钮、筛选胶囊时在点击处迸发十几颗粒子，颜色取自图表同一套六色；
  导航单独用主色系（青 / 浅青 / 蓝 / 深青 / 紫），避免侧栏变成彩虹。
- **理由**：粒子是「确认点击已生效」的即时反馈，尤其在页面跳转有 300ms 过渡时能减少空落感。
  颜色若各写各的，会和图表、标签的颜色体系打架。
- **边界**：只绑 `pointerdown`、只对 `.nav-item / .btn / .chip / .sort-btn` 生效；
  尊重 `prefers-reduced-motion`，关闭动效时完全不加载。

### D-33 文档内嵌图先落盘、再后台补文字（服务 F-11）

- **决策**：docx 解析时按文档顺序抽出内嵌图片，正文对应位置留 `⟦IMG:n⟧` 占位；
  上传响应只做「解析 + 存图 + 入库」，图片文字识别交给 `BackgroundTasks` 的并发 4 路任务，
  完成后把图注补回正文并重建切片。
- **理由**：一份 11MB、20 张图的 docx，串行识别要两三分钟，放在请求里用户只能干等、
  而且看不出卡在哪一步；图片本身几百毫秒就能落盘，先让用户看到图文排布、文字后补是更合理的顺序。
  占位符让图跟着它所在的那段文字走，比「图片统一堆在记录末尾」更接近原始笔记。
- **边界**：占位符只在渲染层替换，入库正文保留原文；图不参与向量化（正文才是依据），
  但图注会被切块索引，所以图里的关键词也能被检索到。删除记录时一并清理磁盘文件。

### D-34 思维导图与知识图谱分工（服务 F-15）

- **决策**：知识图谱（`kg.py`）看**多条记录之间**的章节关系，思维导图（`mindmap.py`）看
  **一份资料内部**的两层结构；两者都让模型抽结构、本地算坐标。
- **理由**：一份六千字的习题解析，在知识图谱里只占一个章节节点，看不出内部结构；
  反过来，多门课混在一张图上，章节名会互相撞（八门课各有「第 5 章」）。
  分开之后各自回答一个具体问题：「这门课由哪几块组成」和「这份资料讲了什么」。
- **边界**：思维导图固定两层、上限 8 个主题 × 8 个要点；坐标按叶子数分配，
  同一份数据每次打开形状一致；结果落 `doc_map` 表，二次打开不调用模型。
  知识图谱增加按课程（标签）切换范围，不再默认把所有课混在一起。

### D-35 文本类资料的自然语言化（服务 F-11）

- **决策**：md / txt 走两级处理。第一级本地清洗（`prose.strip_markup`，毫秒级）：
  去标题井号、列表短横线、加粗星号、表格竖线，并把常见 LaTeX 命令换成 Unicode 符号
  （`\frac12` → `1/2`、`\sqrt{m/k}` → `√(m/k)`、`\omega` → `ω`）。第二级让模型按段转写，
  公式统一成「T = 2π√(m/k)」这类普通文本。
- **理由**：排版稿原样入库，列表摘要里读起来是源码；中文分词把符号当边界，
  `$x=A\cos(\omega t+\varphi)$` 这种串检索命中率极低。而思维导图、知识图谱都从正文抽结构，
  公式没转成普通文本，抽出来的节点就是「简谐振动方程：$x = A\cos(\omega t +」这种半截字。
- **质量闸门**：模型输出必须达到输入的 75%（`MIN_KEEP`）。第一版提示词写「改写成自然语言」，
  模型理解成「总结」，5417 字的资料压成 1953 字，公式还在但推导过程和分支条件没了 ——
  这种输出比原文更难用。低于阈值就整块丢弃，退回本地清洗结果。
- **时机**：本地清洗版先入库，响应立即返回；模型转写放后台，改完替换正文并重建索引。
  三千字的 Markdown 分三块并发也要 30 秒，卡在上传请求里等，用户会以为页面挂了。

### D-41 环形图按记录类型、雷达图按能力域（服务 F-12）

- **决策**：概览页的环形图改成按五个记录类型分段（标题「内容构成」），
  图例直接跳对应分类页；放大视图的雷达图仍按能力域展开。
- **理由**：能力域要先过标签映射，没标签或标签不在映射表里的记录只能落进「其他」；
  而占比 <5% 的小域又会被合并成另一个「其他」—— 图例里于是并排出现两个「其他」，
  各 2 条，读者根本分不清。记录类型是每条记录必有的属性，没有映射、不需要兜底，
  标签也是一眼能懂的词。两个图由此分工：环形看「经历结构」，雷达看「能力覆盖」。
- **副作用**：环形图不再需要「小域合并」逻辑，`MIN_SHARE` 那一段整体删掉。
- **连带影响**：细分视图 `openDetail(ref)` 原来只在 `SECTORS` 里查目标，
  改口径后 `SECTORS` 是记录类型、雷达轴的 key 是能力域名，两者对不上 ——
  点轴和点清单行都会静默返回，什么都不发生。现在两处都查（先 `SECTORS` 后 `RADAR`），
  并由后端把该域的 `tags` / `records` 一起带进 `spokes`（原来只有 label/value/color）。
  记录类型没有下一层可拆，元素带 `href` 时直接跳分类页，不留空态整圆。

### D-42 能力域的兜底匹配（服务 F-12）

- **决策**：`capability_buckets` 在主标签匹配失败时，用记录标题在映射表的标签名里再找一次；
  仍不命中才计入「其他」。映射表新增「专业基础」域（物理 / 数学 / 电路等）。
- **理由**：用户新传的物理资料标签是「大学物理」，映射表里没有，一条有明确领域的记录
  就被扔进了「其他」，雷达图上看不出它属于哪块。标题里就写着「物理」，
  关键词匹配一次就能归位，比让用户手工去维护映射表便宜得多。
- **限制**：只做子串匹配、取第一个命中，不做分词或语义相似度 —— 这条规则要足够可预测，
  归错域比不归更糟，所以宁可保守。

### D-44 标签口径：任意标签都能筛（服务 F-12）

- **决策**：分类页的标签胶囊、按标签筛选、标签文件夹、图谱的标签范围，统一改成
  「这条记录挂着这个标签」即命中，不再只看主标签（第一个）。
- **理由**：早先只认主标签，是为了让「文件夹上的数字」与「点进去的条数」严格相等。
  但代价是次标签在界面上等于不存在 —— 用户给记录打了「英语 + 学习方法」，
  分类页只显示「英语」，「学习方法」既看不到也筛不到。**打了标签却找不到，
  比数字加不齐更难解释。** 计数同步改成 `COUNT(DISTINCT 记录)`，两边仍然一致，
  只是各标签条数之和会大于记录总数。
- **不变**：能力域归类（`capability_buckets`）仍按主标签 —— 一条记录只能归一个能力域，
  否则雷达图合计会超过总数。

### D-45 即时反馈用轻提示（服务全局）

- **决策**：新增 `window.toast(text, {type})`，固定在视口顶部中间，2.8 秒自动退场；
  删除、批量删除、删卡都走它。原来首页顶部那条静态「记录已删除」提示删掉。
- **理由**：列表里的删除发生在页面下半部分，顶部提示要滚回去才看得到 —— 等于没提示。
- **实现**：`aria-live="polite"` 让读屏软件也能播报；服务端需要提示时设 `window.__flash`，
  由全局脚本统一弹出，模板里不用各写一套。

### D-46 长按代替右键（服务全局）

- **决策**：触屏长按 500ms 弹出与右键相同的菜单（查看 / 编辑 / 删除 / 多选）。
- **实现要点**：手指移动超过 10px 立即取消（列表要竖向滚动，按住不动一小会儿很常见）；
  长按后浏览器会补一个 click，用 `longPressed` 标志拦掉，否则卡片当场跳走；
  `touchend` 里 `preventDefault` 并配 `passive: false`。

### D-47 面试预演结果缓存（服务 F-09）

- **决策**：结果存 `interview_cache`，key 是 `(document_id, body_hash)`。打开页面先看缓存，
  「换一批」才重新生成；正文一改 hash 不符，缓存自动作废。
- **理由**：一次生成 15–20 秒还带一次联网检索，同一条记录反复看没必要每次重来。
- **坑**：payload 里的 `doc` 是 `sqlite3.Row`，不能直接 `json.dumps`。
  第一版没剔掉，异常被 `try` 吞了，表现是「缓存永远不命中」——存的时候静默失败。

### D-43 页脚按页面给信息（服务全局）

- **决策**：页脚改成 `{% block footer_note %}`，由各模板覆盖；有数字的用本页真实数字
  （记录数、卡数、章节数、字数），没有的就说这一页能干什么。空态另有说法。
- **理由**：同一句话贴在十几个功能完全不同的页面上，既没提供信息，也谈不上调性 ——
  这句话本身是「面试预演」的立场，放在检索、分类、图谱页上都不成立。
- **实现细节**：中文长句在窄屏容易掉一个孤字（「段。」单独一行），
  页脚加 `text-wrap: pretty`；不支持的浏览器退化为普通换行，不报错。

### D-39 返回链接按来处走（全局）

- **决策**：详情页顶部「返回」不写死概览，由入口链接用 `?from=` 带来源
  （cards / search / category / interview），后端白名单映射成目标地址与文案，
  白名单之外一律按概览处理。
- **理由**：从要点卡点进来、看完却跳回概览，等于把人丢回起点，还得重新点一遍卡片。
  用 `from` 而不是 `Referer`：Referer 会被隐私设置剥掉，也会在刷新后失效。
- **实现细节**：FastAPI 里参数名不能用 `from`（Python 关键字），
  用 `Query("", alias="from")` 接收。

### D-40 侧栏 sticky 的优先级陷阱（服务全局布局）

- **决策**：侧栏折叠样式只用 `#side{transition:width}`，**不写 `position`**。
- **理由**：`#side` 是 ID 选择器，优先级高于 Tailwind 的 `md:sticky` 类。
  上一轮为了让折叠按钮能用 `absolute` 定位，顺手写了 `position:relative`，
  结果把 sticky 顶掉，页面一滚侧栏就跟着走 —— 而 sticky 本身就是定位元素，
  `absolute` 子元素挂在它上面完全成立，那个 `relative` 纯属多余。

### D-37 记录卡片的右键操作与多选（服务 F-01 / F-06）

- **决策**：记录卡片支持右键菜单（查看 / 编辑 / 删除 / 多选），删除走页面中央的自定义弹窗，
  确认后原地移除卡片、不整页刷新；多选态下卡片变实心品牌色、文字反白，底部浮条给批量操作。
- **理由**：删一条记录原本要「进详情 → 点编辑 → 拉到页面底部 → 点删除」四步，
  而删除是高频动作。浏览器原生 `confirm()` 无法定制、样式与站点完全脱节，
  且在移动端表现为模态阻塞。
- **实现**：菜单是 `position:fixed` 贴在鼠标处，滚动或点击外部即关闭；
  删除接口按 `X-Requested-With: fetch` 分流 —— 脚本调用回 JSON，表单提交仍整页跳转。
  批量删除逐条走 `delete_document`（而不是一条 SQL 删多行），
  因为它还要清切片、删磁盘图片、失效向量缓存，绕开就会留孤儿文件。

### D-38 分类页面的图谱命名（服务 F-14）

- **决策**：图谱名称按分类区分（知识图谱 / 技能图谱 / 竞赛图谱 / 项目图谱 / 特长图谱），
  常量放在 `ingest.GRAPH_LABEL`，分类页入口与图谱页标题共用同一份。
- **理由**：五个分类组织结构的逻辑本来就不同（课程按章节、技能按能力项、竞赛按时间线），
  统一叫「知识图谱」会让页面失去辨识度，也说不清这张图在组织什么。

### D-36 导图节点可回到原文（服务 F-15）

- **决策**：模型生成节点时同时给出 `detail`（一句解释）和 `quote`（正文里逐字摘录的 8–20 字）。
  点节点打开 `/doc/{id}?hl={quote}`，详情页把这段文字包成 `<mark id="cited">` 并滚动到视口中央。
- **理由**：导图的价值是「快速定位到该复习的段落」，不是替代原文。只给节点名，
  用户还得自己在长文里找；给了摘录就能一步跳过去。这也是「内容过多」时的出口 ——
  节点受宽度限制只能显示十几个字，完整内容在详情页里。
- **容错**：摘录与正文可能差一个空格或标点，匹配时把空白折叠成 `\s+`；仍找不到就用前 10 个字再试；
  再不行就当普通打开，不报错、不 404。

## 4. 数据模型

```
users(id, email, password_hash, created_at)

documents(id, user_id, kind, title, body, period, source_kind, source_url, created_at)
  kind: course | skill | award | project | trait
  period: YYYY-MM-DD，精确到日；旧数据启动时补齐为当月 1 日
  source_kind: seed | paste
  （表名沿用 documents；语义即《规格书》中的「成长记录」）

chunks(id, document_id, seq, text, seg_text, embedding, created_at)
  seg_text: jieba 分词后的空格串（供 FTS5）
  embedding: bge-m3 的 1024 维向量，JSON 文本（供语义召回）

chunks_fts(chunk_id, seg_text)          -- FTS5 虚拟表

tags(id, user_id, name)
document_tags(document_id, tag_id)

cards(id, user_id, document_id,
      what, result, ability, todo,       -- 做了什么 / 结果如何 / 证明什么能力 / 还可补充
      created_at)
```

**设计说明**
- `chunks` 与 `chunks_fts` 分离：FTS 表只存分词结果，改分词策略后可整表重建。
- `cards` 四字段对应 F-06 的四个维度；`result` 允许为「原文未给出量化结果」，禁止编造。
- `kind` 是 F-03 分类筛选与 F-07 证据分类的依据，索引建在 `(user_id, kind)`。

## 5. 核心链路设计

### 5.1 导入链路（F-02）

```
表单提交 → 校验（非空、≤50k 字）
        → 写 documents
        → 切块（段落优先）
        → 逐块 jieba 分词
        → 写 chunks + chunks_fts
        → 303 跳详情页
```

### 5.2 问答链路（F-04、F-05）

```
问题
 ├─ ① 意图判断：是否为"提问"（而非闲聊）
 ├─ ② 关键词召回：jieba → FTS5 → Top20
 ├─ ③ 模型重排：把 20 条编号候选交给模型，要求返回最相关的 5 个编号
 │     └ 失败/超时 → 用原顺序（L1 降级）
 ├─ ④ 上下文组装：每段标注 [n] 标题 · 片段号
 ├─ ⑤ 生成：强约束"只依据以下片段，无依据就说没有"
 │     └ 接口不可用 → 直接返回原文 Top3（L2 降级）
 ├─ ⑥ 引用校验：回答中的 [n] 必须在引用列表内，否则重试一次
 └─ ⑦ 流式返回正文 + 结束后返回引用数组
```

### 5.3 蒸馏链路（F-06）

```
文档正文（截断到 6000 字）
  → prompt（含 JSON Schema）
  → 解析
      ├ 成功 → 删除该文档旧卡片 → 写入新卡片
      └ 失败 → 重试 1 次 → 仍失败则报错，不写半成品
```

### 5.4 岗位匹配链路（F-07）

```
JD 文本
 ├─ ① 拆解：模型把 JD 拆成 3–10 条「要求条目」（技能/经历/成果三类）
 ├─ ② 逐条检索：每条要求去档案召回 Top5 切片（F-04 复用）
 ├─ ③ 证据判定：有命中 → 记为 evidence（含记录 ID、片段、对应要求）
 │              无命中 → 记为 gap（附 JD 原文短语）
 ├─ ④ 分维度评分（规则计算，非模型打分）
 │      技能匹配 = 技能类要求命中数 / 技能类要求总数
 │      经历相关 = 命中证据覆盖的不同记录数 / min(要求数, 5)
 │      成果证明 = 命中记录中「竞赛/项目」类占比
 │      总分 = 100 × (0.4·技能 + 0.4·经历 + 0.2·成果)
 ├─ ⑤ 简历条目生成：把命中片段改写成 1–2 句「做了什么 + 结果」
 │      → 实体校验：改写前后数字/奖项/时间必须一致，否则丢弃该条
 └─ ⑥ 输出：总分 + 三维分 + 证据 + 缺口 + 条目（每条带来源记录 ID）
```

**为什么分维度用规则算**：`AC-07-5` 要求总分可由分维度重算得出。
若让模型直接给总分，同一份输入两次结果不同，这条验收就无法通过 —— 可复现性本身就是设计目标。

### 5.5 无依据时的统一行为

| 场景 | 行为 |
|---|---|
| 问答无命中（F-05） | 「你的档案里没有相关记录」 |
| 匹配无证据（F-07） | 总分 0，提示「未找到相关记录，建议先补充」 |
| 提炼无内容（F-06） | 报错，不写卡片 |

三处必须一致：**宁可说没有，不许编一个。**

## 6. 模型接入方案

CodeArts 提供免费的 GLM-5.3 / DeepSeek / Kimi。接入按 OpenAI 兼容协议处理：

```bash
LLM_BASE_URL=<CodeArts 或 ModelArts Studio 的兼容端点>
LLM_API_KEY=<控制台生成的 key>
CHAT_MODEL=<glm / deepseek / kimi 的具体模型名>
```

**待确认项（D1 必须落地）**：CodeArts 的模型能力若仅存在于 IDE 对话框、不提供 HTTP 接口，则本方案降级为：
- 用任一 OpenAI 兼容的免费额度（如硅基流动）作为运行后端；
- 答辩时说明「模型层已抽象，可切换至 CodeArts 提供的模型」。

**这两条路都不影响交付**，因为 D-04 的抽象层已经把模型变成了配置项。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 模型接口不可用 | 问答与匹配全废 | D-04 三级降级；检索、录入、浏览不受影响 |
| 模型响应慢（>10s） | 演示卡顿 | 限制候选数、缩短上下文、预生成 5 个示例问答兜底 |
| **简历条目编造数字** | 求职场景致命，且直接违反 AC-07-4 | 实体校验：改写前后的数字/奖项/时间必须在原文中出现，否则丢弃。这是本项目最不可妥协的一条 |
| **模型用课外知识作答** | 学生无法分辨对错 | 课程助手强制每句挂资料编号，无编号即丢弃（D-16）；问答用无依据拒答 |
| 视觉模型额度不足 | 图片导入失败 | 明确提示改用文本粘贴；`.env` 可切换 `VISION_MODEL` 档位 |
| 手机原图过大 | 请求体超限、识别变慢 | 服务端压缩到最长边 1600 再送模型；单文件上限 15MB |
| 中文专业术语切不准 | 召回失败 | 加自定义词典（约 30 个术语），D2 校准 |
| 提炼输出 JSON 不稳定 | 卡片为空 | Schema + 示例 + 重试 1 次；仍失败降级为只展示原文要点 |
| 验收记录写不完 | 直接扣分 | 验收表在编码当天填，不攒到最后 |
